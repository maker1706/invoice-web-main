# 노션 기반 견적서 관리 시스템 개발 로드맵

노션을 데이터베이스로 활용하여 견적서를 관리하고, 클라이언트가 웹에서 조회 및 PDF 다운로드할 수 있는 시스템의 개발 로드맵입니다.

> 📋 요구사항 상세는 [PRD.md](./PRD.md)를 참조하세요.

## 개요

| 구분        | 내용                                                         |
| ----------- | ------------------------------------------------------------ |
| 목표        | 최소 기능으로 빠르게 출시 후 사용자 피드백 기반 개선         |
| 핵심 기능   | F001 노션 연동 · F002 견적서 조회 · F003 PDF 다운로드        |
| 지원 기능   | F010 URL 생성 · F011 유효성 검증 · F012 반응형 레이아웃      |
| 기술 스택   | Next.js 15.5.3, React 19, TypeScript 5, TailwindCSS v4, shadcn/ui, @notionhq/client, @react-pdf/renderer |
| 총 예상기간 | 약 **9~13일** (1인 개발, 하루 4~6시간 기준)                  |

## 1단계: 프로젝트 초기 설정 (골격 구축)

**⏱ 예상 소요 시간**: 1~2일

### 작업 내용

- [ ] Next.js 15.5.3 프로젝트 구조 및 Turbopack 개발 환경 검증
- [ ] TypeScript(strict), ESLint, Prettier, Husky + lint-staged 설정 확인
- [ ] `npm run check-all` 통합 검사 스크립트 동작 확인
- [ ] TailwindCSS v4 + shadcn/ui(new-york) 초기화
- [ ] Notion Integration 생성 및 견적서/항목 데이터베이스 2개 구성 (PRD 데이터 모델 기준)
- [ ] 환경 변수 설정: `.env.local`, `.env.example` (`NOTION_API_KEY`, `NOTION_DATABASE_ID`)
- [ ] App Router 라우트 골격 생성
  - `app/invoice/[id]/page.tsx` (견적서 조회, 빈 골격)
  - `app/not-found.tsx` (404, 빈 골격)
  - `app/layout.tsx` (루트 레이아웃)
- [ ] 노션에 테스트용 샘플 견적서 데이터 2~3건 입력

### 왜 이 순서인가?

모든 후속 작업은 **실행 가능한 개발 환경**과 **실제 데이터 소스(노션)** 가 있어야 검증할 수 있습니다. 환경 변수·노션 권한 문제는 뒤로 미룰수록 원인 파악이 어려워지므로, 가장 먼저 연결 가능 여부를 확인합니다. 또한 라우트 골격을 먼저 잡아두면 이후 기능 개발이 "어디에 들어갈지" 고민 없이 진행됩니다.

### 완료 기준

- [ ] `npm run dev` 실행 시 오류 없이 기동되고 `/invoice/test` 골격 페이지가 열림
- [ ] `npm run check-all`, `npm run build` 모두 통과
- [ ] 노션 API 토큰으로 데이터베이스 조회 호출이 성공 (간단한 스크립트로 확인)
- [ ] `.env.local`이 git에서 제외되고 `.env.example`이 존재

## 2단계: 공통 모듈/컴포넌트 개발

**⏱ 예상 소요 시간**: 1~2일

### 작업 내용

- [ ] **타입 정의** (`any` 금지)
  - `Invoice`, `InvoiceItem`, `InvoiceStatus` 인터페이스 (PRD 데이터 모델 기준)
  - Notion API 응답 타입 및 에러 타입 (`InvoiceNotFoundError` 등)
- [ ] **Zod 스키마**: 노션 응답을 앱 도메인 타입으로 검증/변환
- [ ] **Notion 클라이언트 모듈**: `lib/notion/client.ts` 싱글톤 초기화
- [ ] **유틸리티**: 통화 포맷(원화), 날짜 포맷, 노션 페이지 ID 형식 검증
- [ ] **shadcn/ui 컴포넌트 추가**: `card`, `button`, `table`, `badge`, `separator`, `skeleton`
- [ ] **공통 레이아웃 컴포넌트**: 페이지 컨테이너, 헤더/푸터
- [ ] **견적서 표시용 공통 컴포넌트(데이터 없이 props만 받는 형태)**
  - `StatusBadge`, `InvoiceItemsTable`, `AmountSummary`, `ErrorMessage`

### 왜 이 순서인가?

핵심 기능(노션 조회, 웹 뷰어, PDF)은 **같은 타입과 포맷 유틸을 공유**합니다. 웹 뷰어와 PDF 템플릿이 각자 금액·날짜 포맷을 만들면 결과가 어긋나기 쉽습니다. 공통 모듈을 먼저 만들면 중복을 막고, 핵심 기능 단계에서는 비즈니스 로직에만 집중할 수 있습니다.

### 완료 기준

- [ ] 모든 도메인 타입이 정의되고 `any` 사용이 0건
- [ ] 포맷 유틸 함수가 대표 케이스(0원, 큰 금액, 잘못된 날짜)에서 올바른 결과 반환
- [ ] 공통 컴포넌트가 샘플 props로 렌더링됨 (임시 페이지에서 시각 확인)
- [ ] `npm run check-all` 통과

## 3단계: 핵심 기능 개발

**⏱ 예상 소요 시간**: 3~4일

PRD의 MVP 핵심 기능 **F001 → F002 → F003** 순서로 진행합니다.

### 3-1. F001 노션 데이터베이스 연동 (1~1.5일)

- [ ] `lib/notion/invoice.service.ts`: 페이지 ID로 견적서 조회 (`pages.retrieve`)
- [ ] 연결된 항목(Relation) 조회 및 `InvoiceItem[]` 변환
- [ ] 노션 속성 → 도메인 타입 매핑 (Zod 검증 포함)
- [ ] Notion API 오류(404, 401, 429) 구분 처리
- [ ] 서버 사이드 전용으로 격리 (API 키 클라이언트 노출 방지)

### 3-2. F002 견적서 조회 (1~1.5일)

- [ ] `/invoice/[id]` Server Component에서 서비스 호출 후 렌더링
- [ ] 발행일, 유효기간, 클라이언트명, 항목별 금액, 총액 표시
- [ ] 2단계 공통 컴포넌트를 조합해 견적서 레이아웃 완성
- [ ] 로딩 UI(`loading.tsx`, Skeleton) 적용

### 3-3. F003 PDF 다운로드 (1~1.5일)

- [ ] `@react-pdf/renderer` 설치 및 `InvoicePDF` 템플릿 컴포넌트 작성
- [ ] **한글 폰트 등록** (Noto Sans KR 등) — 한글 깨짐 방지
- [ ] `app/api/generate-pdf/route.ts` (또는 `/invoice/[id]/pdf`) 구현
- [ ] 다운로드 버튼 컴포넌트 + 생성 중 로딩 상태 표시
- [ ] 파일명 규칙: `견적서_{invoice_number}.pdf`

### 왜 이 순서인가?

의존 관계가 **데이터 → 화면 → 파일 출력** 순으로 이어집니다. 노션 데이터를 가져오지 못하면 화면을 만들 수 없고, 화면에 표시할 데이터 구조가 확정되어야 PDF 템플릿을 같은 구조로 만들 수 있습니다. 또한 가장 불확실성이 큰 부분(노션 Relation 처리, PDF 한글 폰트)을 MVP 가치의 중심에서 먼저 검증합니다.

### 완료 기준

- [ ] 실제 노션 견적서 ID로 접속 시 모든 필드가 정확히 표시됨 (노션 원본과 대조)
- [ ] 항목 합계와 총액이 노션 값과 일치
- [ ] PDF 다운로드 버튼 클릭 시 한글이 깨지지 않은 PDF가 다운로드됨
- [ ] 서비스 로직과 PDF 라우트를 Playwright MCP로 테스트 완료
- [ ] 브라우저 번들에 `NOTION_API_KEY`가 포함되지 않음 확인

## 4단계: 추가 기능 개발

**⏱ 예상 소요 시간**: 2일

핵심 기능이 동작한 뒤, 사용성과 안정성을 보완하는 **PRD 지원 기능(F010~F012)** 을 완성합니다.

### 작업 내용

- [ ] **F011 견적서 유효성 검증**
  - 존재하지 않는 ID, 잘못된 형식의 ID → `notFound()` 처리
  - 접근 권한 없음/API 오류 시 구분된 에러 UI (`error.tsx`)
  - 404 페이지: "견적서를 찾을 수 없습니다" + 발행자 문의 안내
- [ ] **F012 반응형 레이아웃**
  - 모바일: 항목 테이블을 카드형으로 전환 또는 가로 스크롤 처리
  - 태블릿/데스크톱 레이아웃 정리
  - 인쇄(`@media print`) 스타일 보완
- [ ] **F010 고유 URL 안내**
  - 노션에서 URL을 쉽게 만들 수 있도록 안내 (노션 페이지 ID 기반 URL 규칙 문서화)
  - 선택: 노션 수식 속성으로 견적서 링크 자동 생성 예시 제공
- [ ] 상태(`status`) 뱃지 표시 및 유효기간 만료 시 안내 문구
- [ ] 접근성 보완 (aria 속성, 키보드 포커스, 색상 대비)

### 왜 이 순서인가?

예외 처리와 반응형은 **정상 동작하는 기본 화면이 있어야** 올바르게 검증할 수 있습니다. 핵심 기능 전에 만들면 화면 구조가 바뀔 때마다 다시 작업해야 합니다. 반대로 이 단계를 배포 직전에 몰아서 하면 "잘못된 URL 접근" 같은 기본 시나리오가 누락될 위험이 있으므로, 최적화 전에 기능을 완결합니다.

### 완료 기준

- [ ] 존재하지 않는 ID, 형식 오류 ID 접근 시 404 안내 페이지 표시
- [ ] 360px / 768px / 1280px 너비에서 레이아웃이 깨지지 않음
- [ ] 노션 API 장애 시 앱이 크래시하지 않고 에러 UI 표시
- [ ] PRD의 **MVP 성공 기준 5가지** 모두 수동 검증 완료

## 5단계: 최적화 및 배포

**⏱ 예상 소요 시간**: 2~3일

### 작업 내용

- [ ] **성능 최적화**
  - 노션 조회 캐싱 전략 결정 (`revalidate` 또는 `unstable_cache`) — 실시간성과 API 호출 제한(429)의 균형
  - PDF 생성 동적 import 및 번들 크기 점검
  - 폰트 서브셋/로딩 최적화
  - Lighthouse 점검 (Performance, Accessibility, SEO)
- [ ] **보안 점검**
  - 환경 변수 서버 전용 확인, 에러 메시지에 내부 정보 노출 여부 점검
  - `robots` 메타 `noindex` 적용 (견적서 URL 검색 노출 방지)
  - PDF 라우트 입력값 검증 (Zod)
- [ ] **테스트**
  - Playwright MCP로 E2E 시나리오 (정상 조회 / 404 / PDF 다운로드 / 모바일 뷰)
  - 크로스 브라우저 확인 (Chrome, Safari, Firefox)
- [ ] **배포**
  - Vercel 프로젝트 연결 및 환경 변수 등록 (`NOTION_API_KEY`, `NOTION_DATABASE_ID`)
  - 프리뷰 배포 → 프로덕션 배포
  - PDF 생성 함수 타임아웃/메모리 설정 확인
- [ ] **문서화**: README, 노션 데이터베이스 설정 가이드, 배포 체크리스트

### 왜 이 순서인가?

최적화는 **측정할 대상(완성된 기능)** 이 있어야 의미가 있고, 기능이 바뀌면 측정 결과도 달라집니다. 배포는 모든 검증이 끝난 마지막 단계이며, 로컬에서 되던 PDF·환경 변수가 서버리스 환경에서 실패하는 경우가 흔하므로 **프리뷰 배포로 먼저 검증**한 뒤 프로덕션에 반영합니다.

### 완료 기준

- [ ] `npm run check-all` 및 `npm run build` 통과
- [ ] Lighthouse Performance / Accessibility 90점 이상
- [ ] 프로덕션 URL에서 실제 노션 견적서 조회 및 PDF 다운로드 성공
- [ ] E2E 시나리오 전체 통과
- [ ] 배포 체크리스트와 사용 가이드 문서 작성 완료
